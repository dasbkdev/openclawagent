# Starlab Agent — правила проекта

Внутренняя система AI-ассистентов компании: Telegram-бот + центральный
control-plane на Linux VPS + локальные desktop-агенты (форк OpenClaw).
Подробный контекст: `STARLAB_AGENT_FULL_HANDOFF_RU.md`. Журнал всех работ:
`CODEX_WORKLOG_FOR_CLAUDE.md` — каждая выполненная задача фиксируется там.

## Карта репозитория

- `control-plane/` — основной backend (Node.js ≥22.19, zero-dependency, ESM).
  Два процесса: `src/server.js` (HTTP API, 127.0.0.1:3099) и
  `src/telegram-bot.js` (long-polling бот). Слои: `api/` → `domain/` →
  `connectors/` → `integrations/` → `setup/` → `infra/`.
- `n8n/` — workflow-экспорты и генераторы для n8n (Docker на сервере).
- `openclaw-starlab-2026.6.5/` — vendored-форк OpenClaw для desktop-агентов.
- `control-plane/desktop-agent/` — Electron-агент устройства.
- Рабочая ветка: `server`. Production: `195.238.122.228` / starlabagent.pp.ua.


## Жёсткие правила (нарушение недопустимо)

1. **Рабочий код проекта не изменять без отдельного подтверждения
   пользователя.** Конфигурация Claude Code и документация — можно.
2. Не читать, не логировать и не коммитить секреты: `**/secrets.json`,
   `**/secrets.key`, `**/.env`, API-ключи, токены, пароли, OAuth JSON.
3. Не коммитить: `kickidler/`, `openclaw/`, `metricon/`, runtime state,
   `*.exe`/`*.dmg` инсталляторы.
4. Все интеграции (Metricon, Platrum, Bitrix, YouGile, Google) — read-only;
   write только через draft + confirm; delete запрещён всегда.
5. Production (`/var/lib/company-control-plane`, systemd, nginx) — только
   после backup и только с подтверждения пользователя.
6. Именование: `kickidler` в коде = Metricon в продукте; Bitrix — legacy,
   основной источник задач — Platrum.
7. Секреты задаются только через `/setup` wizard (encrypted store),
   не через `.env` руками.

## Известные архитектурные риски (учитывать при любом изменении)

- Два процесса (API + бот) пишут в один `control-plane.json`;
  `JsonStore.writeChain` сериализует записи только внутри процесса —
  межпроцессные гонки возможны. Не добавлять новых писателей state.
- Аутентификация внутренних API — заголовок `X-Actor-Telegram-Id` без
  подписи; новые внутренние endpoints защищать токеном
  (как `/api/v1/automation/*` через `X-Automation-Token`).
- Telegram-конвейер существует и в control-plane, и в n8n — не расширять
  дубль без решения о единственном владельце.

## Оркестрация агентов

Главный агент сессии — **Architect** (Fable 5). Для каждой задачи он:

1. Анализирует задачу в контексте архитектуры.
2. Составляет план: шаги, файлы, риски, способ проверки.
3. Оценивает сложность по матрице ниже.
4. Делегирует исполнителю самодостаточный промпт (субагент стартует с
   чистым контекстом: указать файлы, правила, ожидаемую проверку).
5. Проверяет результат: `npm test`, `git diff`, соответствие правилам.
6. Фиксирует работу в `CODEX_WORKLOG_FOR_CLAUDE.md`.

### Матрица выбора исполнителя

| Сложность | Признаки | Исполнитель |
|---|---|---|
| Простая | 1–2 файла, есть аналогичный код, тесты очевидны | `developer` (Sonnet) |
| Средняя | 3–5 файлов, новая команда бота / endpoint / отчёт, документация | `developer` (Sonnet) |
| Сложная | Архитектура, миграция хранилища, memory system, OAuth/токены, RBAC/безопасность, OpenClaw-форк, device agents, граница n8n, systemd/nginx/деплой | `expert` (Opus) |
| Критическая | Production-state, секреты, аутентификация | `expert` + план утверждается пользователем до выполнения |

### Правила делегирования

- Architect не пишет код сам для простых/средних задач — делегирует.
- Спорная сложность → трактовать вверх (к `expert`).
- Результат субагента всегда проверяется Architect'ом перед сдачей.
- Субагенты подчиняются всем жёстким правилам этого файла, включая
  правило №1 (подтверждение пользователя на изменение рабочего кода
  получает Architect до делегирования, не субагент).
